# Assets

Assets are Openlane's asset inventory: the systems, services, devices, domains, and repositories your organization runs, managed in the same system as the compliance automation built around them. Each record carries ownership, classification, and the relationships that connect it to controls, scans, and evidence, and records can be curated by hand, imported in bulk, or discovered through integrations.

Keeping asset management and compliance together means the inventory frameworks require is the same one your program operates on, with nothing to reconcile between tools. ISO 27001 A.8 requires an inventory of information and associated assets, SOC 2 CC6 and CC7 assume you can enumerate the systems where access is controlled and monitored, and HIPAA expects you to know which systems hold ePHI. Auditors typically start from the inventory: they pick assets and ask who owns each one, what data it holds, and what evidence covers it, and asset records are built to answer exactly those questions.

## How Assets Work

Each asset record remembers where it came from: entered by hand, imported, or discovered by an integration, with machine-sourced records keeping their source platform and when they were last observed. Every asset declares what kind of resource it is, whether an application or service, a domain, a device, a source repository, or a telephony resource.

Classification carries much of the record's value: environment, criticality, data classification, and similar fields all draw from your organization's [custom enums](../settings/custom-data.mdx), so records are categorized in your vocabulary rather than a vendor's. Ownership can be a user, a group, or a named person who does not have an account yet, so accountability never depends on everyone being an Openlane user.

Assets connect to the vendor [entities](./entities.mdx) that supply them, the [platforms](./platforms.mdx) whose scope they fall inside (or are explicitly excluded from), and the [scans](../exposure/scans.mdx) run against them. For the complete field list, see the [GraphQL object reference](/graphql).

## Working with Assets

### Import the In-Scope Inventory

Start from your existing source of truth (a cloud console export, an ITAM report, a spreadsheet) and cut it down to what is actually in scope for your program before importing via CSV. For each record, set the type, an identifier that matches how the resource is known elsewhere, the region, and whether it contains PII. Then assign an owner to every asset; the inventory only functions as a control when each record has an accountable person behind it.

### Classify for Filtering and Evidence

Apply environment, data classification, and criticality values so the inventory can answer scoped questions: production assets containing PII, critical assets without an encryption status, assets in a given region. These are the exact cuts auditors and security reviews ask for, and classification lets you answer each one with a filter. Because the classification values are [custom enums](../settings/custom-data.mdx), you can shape them to match how your organization already talks about its systems.

### Connect Assets to Security Work

Registry scope feeds the [exposure workflow](../exposure/overview.mdx): scans run against assets, and the resulting vulnerabilities and findings trace back to the affected records. Linking assets to their scans means "what is the security posture of this system" and "which in-scope assets have never been scanned" are both queries against the registry rather than tribal knowledge.

### Map Dependencies

Relate each asset to the vendor entities behind it and the platforms it composes. When a vendor has an incident, the entity's linked assets tell you your exposure; when an auditor reviews a platform, its linked assets show what sits inside the boundary. Asset-to-asset connections capture dependencies between resources themselves, so upstream and downstream impact stays visible.

## FAQ

<details>
<summary>Should I import my entire CMDB?</summary>

No. We recommend importing only what is in scope for your compliance program, because every asset you list is an asset an auditor can sample, so an inventory padded with unowned, unclassified records weakens your position rather than strengthening it. A useful test: if nobody would notice the record going stale, it probably does not belong in the compliance inventory.

</details>

<details>
<summary>What is the difference between an asset and a platform?</summary>

An asset is an individual resource: a service, domain, device, or repository. A [platform](./platforms.mdx) is a governed system boundary that assets compose, carrying the scope statement, ownership roles, and system description an audit needs. The production API service, its database, and its DNS domain are assets; "Production API" as the system your SOC 2 report describes is a platform that relates to all three.

</details>

<details>
<summary>How do I tell curated records apart from machine-created ones?</summary>

Check the source type. Manual and Imported records were created or loaded by a person; Discovered and Api records were produced programmatically and carry their source platform, integration, and observed-at timestamp. Filtering on source type lets you review machine-sourced records before treating them as part of your curated scope.

</details>

mutation {
