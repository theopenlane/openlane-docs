# Subcontrols

Some controls are too broad to implement or test as a single unit. Subcontrols split a [control](./overview.mdx) into smaller pieces that can each be implemented, tested, and verified on their own, while keeping the parent control as the thing your framework maps to.

Take a broad access control requirement: the encryption configuration, the approval workflow, and the physical badge system might all live under it, but they're owned by different teams and verified in completely different ways. As three subcontrols, each piece gets its own implementation and its own verification, and the parent control rolls them up.

When an auditor tests a broad control, they test its parts, and "partially implemented" is not a status you want to explain. Splitting a control into subcontrols makes the real state visible: two components verified, one still in progress, each with a specific owner. It also keeps evidence precise, because an artifact attaches to the component it actually demonstrates rather than to a control that covers five different things.

## Working with Subcontrols

Each subcontrol has its own reference code, name, and description, and belongs to exactly one parent control. From there it behaves like a control:

- **Implementations**: a [control implementation](./implementations.mdx) can belong to a subcontrol directly, describing how that specific component operates and who's accountable for it
- **Verification**: each subcontrol is tested independently, so verifying one component doesn't hide gaps in another
- **Categories**: like controls, subcontrols span administrative, technical, and physical territory (see [control categories](./overview.mdx#control-categories)), which is often exactly why the split exists: different categories mean different implementers and different verification methods

For the full field list, see the [GraphQL object reference](/docs/api/graph-api/).

## FAQ

<details>
<summary>When should I split a control into subcontrols?</summary>

When its components have different owners, different implementation types, or different verification methods. If one person implements and one test verifies the whole control, a single [implementation](./implementations.mdx) is simpler; don't split for the sake of splitting.

</details>

<details>
<summary>Do subcontrols map to frameworks separately?</summary>

No, framework mapping happens at the [control](./overview.mdx) level. Subcontrols organize the work underneath a control; the parent is what satisfies the requirement.

</details>

<details>
<summary>Can a subcontrol have its own implementation?</summary>

Yes. That's the point: each subcontrol carries its own implementation narrative and verification, independent of its siblings, and [evidence](../evidence/overview.mdx) collected for it demonstrates exactly that component.

</details>
