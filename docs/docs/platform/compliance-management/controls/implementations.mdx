# Control Implementations

A control says what you're supposed to do. A control implementation says how you actually do it: in your environment, with your tools, run by your people. It's the difference between "we have access controls" and something an auditor can test.

When an auditor samples a control, the implementation is the first thing they read. A specific, current implementation narrative, paired with evidence that matches it, is what makes an audit go smoothly. Vague or stale implementations generate follow-up questions and slow the audit down.

Rolling up implementation status across a framework also shows how far you are from audit-ready.

## Implementation Status

Each implementation moves through four statuses:

| Status | What it means | What moves it forward |
| ------ | ------------- | --------------------- |
| **Draft** | You're still figuring out the approach | Finish the design, get sign-off to implement |
| **In Progress** | Active work underway | Complete the rollout and initial testing |
| **Implemented** | The control is operating | Formal verification that it works as described |
| **Verified** | Tested and confirmed effective | Ongoing monitoring; re-verify on a cadence |

Don't rush to **Verified**. Marking something verified means someone actually tested it; an auditor asking "who verified this and how?" should have a real answer.

## Writing a Good Implementation

The implementation details are prose, and specificity is what makes them useful:

- **Vague (avoid):** "Access to production systems is restricted and reviewed."
- **Specific (aim for):** "Production access requires SSO with hardware MFA and membership in the `prod-access` group. Access reviews run quarterly; the platform team removes non-compliant grants within 5 business days."

A good implementation names the systems, the owners, and the cadence. Write in present tense about what you *do*, not future tense about what you *plan*; plans belong in Draft status.

## Verification and Evidence

Verification confirms the implementation works: someone tests the control (walkthrough, sample inspection, technical test) and records the result and date. From there, [evidence](../evidence/overview.mdx) proves it *keeps* working: recurring artifacts collected over the audit period.

A practical rhythm: verify when you first complete an implementation, attach the test results as evidence, then let recurring [tasks](../../automation/tasks.mdx) drive evidence collection on schedule.

## How Implementations Connect

Each implementation belongs to a [control](./overview.mdx) (or [subcontrol](./subcontrols.mdx)) and has an assignee: the person accountable for keeping it accurate. Because controls map to your enabled frameworks, one well-written implementation can serve the same requirement across SOC 2, ISO 27001, and anything else that maps to it.

## FAQ

<details>
<summary>What's the difference between an implementation and evidence?</summary>

The implementation describes how the control operates; evidence proves it operated during the period. Auditors want both: the narrative and the artifacts that back it up.

</details>

<details>
<summary>Do I need an implementation for every control?</summary>

For every control in scope for your audit, yes; it's what the auditor tests against. Controls you've enabled but haven't operationalized yet are exactly what Draft status is for.

</details>

<details>
<summary>Who should own an implementation?</summary>

We recommend the person who actually runs the process rather than the compliance lead, because they'll know when reality drifts from the write-up. Drift between the two is the most common audit finding.

</details>
